**Date:** 2026-07-16 (16:08–16:35 +03)
**Scope:** Raspberry Pi 5 (`patrolbot-rpi5`, 10.0.0.2) and legacy onboard SBC (`patrolbot1`, 10.0.0.1) over the existing Ethernet link. Strictly read-only: no test connections to the hardware-server port, no serial access, no commands to the robot, no publishing. Robot state during the audit: **docked and charging** (observed live).

## 2. Connection ownership and link audit

### 2.1 Topology (verified from both ends)

```
µARCS controller ──/dev/ttyS0 @9600 baud── socat (PID 998, socat-boot.service)
                                              │ tcp4-listen:7000 (localhost only)
                                     patrolbot_server (PID 1289, user `ros`,
                                       ~/.config/systemd/user/patrolbot-server.service,
                                       args: -rh 127.0.0.1 -rrtp 7000)
SICK LMS-200 ────/dev/ttyS2 (COM3)──────────┘ (fd 4, held directly by patrolbot_server)
                                              │ ArSocket listen *:7272 (backlog 5)
                                              │ ESTAB 10.0.0.1:7272 ↔ 10.0.0.2:49444
Pi 5: bridge_node (PID 1398, container patrolbot-bridge, fd 18) ── ROS 2 topics
```

- **Exactly one hardware-server client exists.** `ss` on both ends shows the single ESTAB pair; the SBC listener has Recv-Q 0 (no queued/abandoned handshakes). The server accepts one client at a time and only re-accepts after disconnect, so any second connector would hang unserved in the backlog (none present).
- **Only one process can reach µARCS:** socat holds ttyS0 exclusively and (no `fork` option) serves exactly one TCP client on 7000; that slot is taken by patrolbot_server. `socat_loop.sh` restarts socat 1 s after exit; `Restart=always/RestartSec=3` restarts the server; `enp2s5-static-ip.sh` re-applies 10.0.0.1/24 every 5 s (ifupdown broken since 2021 — shim is the only thing keeping the link addressed).
- **Health checks create no connections:** the Docker healthcheck on all three Pi containers (`patrolbot-healthcheck`) only greps `/proc` cmdlines — no sockets, no DDS.
- No competing/obsolete startup services found on the SBC (no ROS 1 autostart; the dormant Docker containers, incl. `myros2`, are all Exited). No firewall problems observed; `iptables -L` needs root and was not inspectable with existing credentials.

### 2.2 Protocol (custom text over TCP 7272)

SBC→Pi at 20 Hz: `ODOM:x,y,th,vx,vth|LASER:r1,…\n` plus every 5th frame `AUX:SONAR=x,y;…|BATT=v,soc,cs,temp|FLAGS=flags,fault,stall,motors,estop\n`. Pi→SBC: `DRIVE:linear:angular\n`.

Verified behaviors (source: `patrolbot_server.cpp`, `bridge_node.py` — deployed copies are hash-identical to the repo; nav2 params differ from repo only in comments):

| Requirement | Status |
|---|---|
| Command loss stops motion | ✅ SBC watchdog: no DRIVE for 750 ms → `setVel(0)/setRotVel(0)`. Necessary because ARIA's state reflector re-sends the last velocity forever. |
| SBC-server loss stops motion | ✅ Pi safety watchdog holds (zero Twist at mux priority 10) when /scan or /odom stale >0.5 s; costmap `expected_update_rate` 0.5 s marks buffers not-current; collision monitor stops on stale scan (observed in logs: "Robot to stop due to invalid source"). |
| ROS-side loss stops motion | ✅ mux input timeouts (0.2–1 s) + the 750 ms SBC watchdog. |
| Reconnect does not resume old velocity | ✅ Server zeroes velocity + `stop()` before re-accepting; resets `lastCmdTime` on connect; bridge never re-sends a stored command. |
| TCP state ≠ fresh data | ✅ Server streams an EMPTY `LASER:` field when the SICK's newest reading is >500 ms old → Pi stops publishing /scan → watchdog holds. Bridge additionally discards telemetry lines older than 0.5 s after a publish stall and has a 3 s recv timeout. |
| Per-sensor freshness tracked independently | ⚠️ Partial. Laser: yes (500 ms guard). Odom: no explicit guard, but a µARCS SIP stall drops the ArRobot connection → server exits → restart → detectable. **Sonar/battery/flags: no freshness tracking anywhere; if the AUX line stops, /sonar just silently stops** (tolerable today only because nothing safety-critical consumes it). |
| Motors not auto-re-enabled without a controlled sequence | ❌ **Server calls `enableMotors()` at startup and re-enables (throttled 500 ms) whenever a nonzero DRIVE arrives with motors off.** Any velocity source can un-disable the motors. |
| Checksums / partial packets | ⚠️ No checksums (bare TCP text). Pi handles partial lines via newline framing. SBC `sscanf` parses only the first DRIVE line per 256-byte read and drops fragments — safe direction (watchdog), minor command latency at worst. |
| Unit conversions | ✅ mm↔m, deg↔rad correct in both directions; sonar in robot frame meters; DRIVE m/s→mm/s, rad/s→deg/s. |
| Rear-sonar numbering/direction | ✅ Computed from `.p` mount pose + range × direction (rear units 8–15 at x −83…−263 mm). Observed point (x −3.9, y −0.7) consistent with a rear-left echo. |
| Bumper bit mapping | ⚠️ Raw only. Left/right stall bits decoded per ARIA convention; bumper segment bits exposed as `*_bumper_bits_raw` and **deliberately excluded from the alarm level** ("constant high bit … no bumpers wired / reserved"). Observed constant `left_bumper_bits_raw=8`. Segment mapping unverified. |
| Encoders/gyro integrated once | ✅ Single odometry source (µARCS; gyro is firmware-integrated, `GyroScaler 1.626` in `.p`; no `ArAnalogGyro` in the server). |
| Command rate within limits | ✅ ≤ ~20–25 Hz DRIVE vs 20 Hz server read loop with 255-byte drain; no flooding. Serial leg is 9600 baud — the stock µARCS rate; adequate but a fixed latency floor worth knowing about. |

### 2.3 Overnight outage / restart history (reconstructed)

- Jul 15 ≈ 23:11: telemetry stops mid-connection (bridge recv timeout — silent death, no FIN). Syslog on the SBC contains NUL blocks → **unclean power loss, not a shutdown**.
- ≈ 16.7 h of bridge `connect timed out` (7,533 attempts — SBC unpowered/dead) + 5 × host-unreachable (booting).
- Jul 16 ≈ 15:51: SBC boots. Server starts 15:52, SICK fails first configure, ArLaserConnector power-cycles it, laser up ~15:54; server binds 7272 only after laser init (deliberate, documented in source) → 26 "connection refused" retries on the Pi, then a clean single connection that has persisted since. The Pi watchdog held the robot for the entire outage. Whether the power loss was an operator switch-off or a fault cannot be determined remotely — flagged for the operator.
- Journal is volatile (`/var/log/journal` absent) and syslog rotation is wrecked by the frozen clock (every boot logs as "Apr 2 2021"), so long-term restart history is not recoverable on the SBC.
- Also broken: the unit drop-in `StandardOutput=append:…patrolbot_server.log` is silently ignored (needs systemd ≥ 240; Xenial has 229) — the log file has been empty since Jun 28 while output goes to the volatile journal.

## 3. Focused finding: Dock departure (Concern A)

### 3.1 Observed docked state (live, read-only)

- `/battery`: 29.7 V, `power_supply_status: CHARGING` (ARIA charge state > 0).
- `/diagnostics` `patrolbot/base`: **`E-STOP ENGAGED` (estop_pressed True), `motors_enabled False`**, both motor-stall bits set, flags 1060, fault 0.
- `/scan` (25 Hz, fresh): 182 rays; **90 rays are `inf`** — the contiguous sector dead ahead. The bridge maps returns < 0.25 m (`SCAN_RANGE_MIN`) to `inf`, so the dock face/wall closer than 0.25 m is *deleted from the scan*. The visible flanks are at 0.251–0.33 m (≈ −34…−29° and +55…+78°).
- **Exactly 8 scan points fall inside the collision-monitor `stop_box` (±0.3 m)** — equal to its `min_points: 8` trigger threshold ("minimum number of data readings within a zone to trigger the action", verified in the installed Jazzy header). The box is symmetric and direction-agnostic: when triggered it zeroes **all** nav-path commands, including reverse.
- `/sonar` (5 Hz, fresh): real-detection-only points; 1 rear echo at (−3.9, −0.7) — rear area open.
- Localization: `/amcl_pose` and map→base_link TF are exactly (0,0,0) — **not localized**. `always_reset_initial_pose: true` + `initial_pose [0,0,0]` means every stack restart discards the pose until an operator re-initializes.

### 3.2 Component-by-component analysis

| Layer | Reverse capable? | Docked behavior |
|---|---|---|
| µARCS / charging hardware | — | **Observed: e-stop asserted + motors disabled while charging.** Manual: "you can continue operating the PatrolBot, *other than driving it*, while charging" — driving is inhibited by design while the dock mechanism is engaged. µARCS command `CHARGE (68), 0=release / 1=deploy autocharge-docking mechanism` exists to disengage; **no software anywhere in the system ever sends it.** (Caveat: a physically latched red E-stop button would produce the same telemetry; distinguishing them is a deferred physical check.) |
| patrolbot_server (SBC) | ✅ accepts negative DRIVE | No charge interlock of its own; would try `enableMotors()` on a nonzero DRIVE, which cannot override a hardware e-stop assertion. No undock/CHARGE-release command in the protocol. |
| Bridge (Pi) | ✅ passes any Twist | No restrictions. |
| teleop_velocity_smoother / twist_mux | ✅ symmetric limits | No restrictions (smoother ±1.0 m/s; mux has no sign logic). |
| velocity_smoother (nav path) | ✅ `min_velocity [-0.26, 0, -1.0]` | Reverse permitted. |
| collision_monitor | — | **stop_box is fed only by the front /scan; with the dock wall at 0.25–0.30 m it is at/over the 8-point trigger and zeroes any nav command regardless of direction.** Perverse detail: if the robot is parked *closer* than 0.25 m, the wall becomes `inf`, is dropped, and the box may NOT trigger — behavior flips with parking distance. Rear sonar is not an observation source, so reverse motion it *permits* is also *unguarded*. |
| Controller (RPP) | ❌ `allow_reversing: false` | Cannot emit negative linear velocity, ever (and reversing is mutually exclusive with the enabled `use_rotate_to_heading`). Its escape move would be to rotate in place — the front corners sweep the 0.29 m swing radius into a wall < 0.29 m away, with RPP's own collision check disabled (`use_collision_detection: false`). |
| Planner (NavFn) | ❌ forward paths only | Also fails outright while unlocalized. |
| Behavior server `BackUp` | ✅ (0.30 m @ 0.15 m/s in the BT) | The only reverse-capable nav component — but (a) **the custom BT (`navigate_recovery_always_try.xml`) that guarantees the recovery round-robin is NOT wired in** — no `default_nav_to_pose_bt_xml` anywhere, so the stock BT runs and gates recovery behind `WouldA*RecoveryHelp` error classification; (b) BackUp is 4th in the round-robin behind ClearCostmaps → **Spin** (which would grind the swing radius into the wall) → Wait; (c) its cmd_vel flows through the collision monitor and is zeroed by the triggered stop_box; (d) rear costmap cells are informed by *no rear sensor*. |
| opennav_docking `docking_server` | ✅ (undock drives in reverse; `dock_backwards: false`, staging −0.7 m) | Loaded and active but **unused and unusable as configured**: no dock database/poses; `SimpleChargingDock` has no way to send the µARCS CHARGE-release; and it **publishes directly to `/cmd_vel`**, bypassing twist_mux, both smoothers, the collision monitor and the safety-watchdog priority scheme (verified via `ros2 node info`). If ever invoked it would command unguarded motion — and still fail against the charging inhibit. |
| Static map | — | Not evaluable while unlocalized; the map is a CAD-derived plan (known phantom-artifact issues). Whether the dock/wall is drawn there must be checked once localized. |
| Stale obstacles | — | Local costmap: the wall flanks re-mark continuously; rays that go `inf` neither mark **nor clear** (`inf_is_valid` unset → false), so cells marked during the approach (when the wall was > 0.25 m away) persist under the robot's nose while docked. Costmap staleness guards themselves are healthy. |

### 3.3 Root cause and confidence

Refusal to leave the dock is **over-determined** — five independent blockers, in order of bite:

1. **Charging/e-stop motor inhibit (hardware/firmware)** — observed live; manual-documented; no release command implemented. *High confidence that motion is currently impossible while charging; medium confidence on the exact mechanism (dock-asserted vs. latched button) — deferred physical check.*
2. **No dock-exit behavior exists anywhere** (no CHARGE-release, no undock sequence, docking server unconfigured). *High confidence.*
3. **Nav stack cannot command reverse** (RPP `allow_reversing: false`; custom recovery BT with BackUp not actually loaded). *High confidence, from config + code.*
4. **Collision monitor stop_box blocks all directions on front-wall detections at 0.25–0.30 m.** *High confidence; observed 8 points in the box.*
5. **Localization invalid after restart** (AMCL always resets to 0,0,0). *Observed.*

The operator's hypothesis (costmap/footprint blocks departure) is real but **subordinate**: even with a perfect costmap the robot would still be held by items 1–3. Notably the footprint itself is *not* oversized (see §5).

### 3.4 Safe remediation options (preserve collision protection)

1. Implement a **controlled undock sequence** in `patrolbot_server` + protocol (new command, e.g. `UNDOCK`): send `ArCommands::CHARGE 0` (release), wait for charge-state 0, enable motors, then allow a short reverse. Never clear e-stop in software beyond what µARCS permits.
2. **Integrate rear sonar as a collision-monitor source** (`type: "range"`/pointcloud source covering a rear polygon) so reverse motion is guarded, and optionally as a costmap observation source for reversing.
3. Make the stop response **direction-aware**: either use two polygons (front stop polygon acting on forward commands via an `approach` polygon, rear polygon guarded by sonar) or accept the documented Nav2 limitation and gate dock-exit through a dedicated behavior that runs with the rear guard active.
4. **Wire in the custom BT** (`default_nav_to_pose_bt_xml`) so BackUp recovery is actually reachable — or better, add an explicit BackUp-first dock-exit action before any Spin.
5. Route **docking_server output through twist_mux** (remap `cmd_vel` → `input/navi` or a dedicated mux input) before anyone starts using it.
6. Fix AMCL initial pose at the dock (e.g., `set_initial_pose` from the known dock pose on startup, or drop `always_reset_initial_pose`).
7. Do **not** raise `SCAN_RANGE_MIN`, shrink the footprint, lower `min_points`, or remove the wall from the map.

### 4.2 Parameter review (can software see what the hardware sees?)

- Costmap sources: `scan` only, `LaserScan`, marking+clearing enabled, `max_obstacle_height 2.0`, `expected_update_rate 0.5`. `obstacle_range`/`raytrace_range` at defaults (2.5 m / 3.0 m) — adequate at 0.22 m/s.
- No height filter is discarding anything relevant: there is no 3D sensor to filter.
- Bridge `SCAN_RANGE_MIN 0.25` deletes returns < 0.25 m (documented anti-self-occlusion measure). It is a *software* close-range blind ring on top of the physical one — an object that gets within 0.25 m of the laser (e.g., during a turn) vanishes rather than being marked. Kept deliberately (footprint deadlock history); flagged as a residual risk, not a defect to blindly remove.
- Speed/stopping: 0.22 m/s cruise, decel 2.5 m/s² ⇒ ~1 cm braking distance + ~0.3 s pipeline latency ⇒ ≲ 8 cm total. **Stopping distance is not the problem for detected obstacles.**
- Controller: RPP checks the footprint along its arc only when `use_collision_detection` is on — it is **off** (doorway inscribed-band freeze, documented). The stop_box is the sole automatic guard, and it sees only the 30 cm plane.
- Footprint/inflation: correct-sized octagon + 0.40 m inflation. **Per the audit brief's own reasoning requirement: no footprint or inflation value can detect an object that produces no sensor observation.** Nothing in this section fixes Concern B by itself.

### 4.3 Blind-zone statement

Forward-approaching obstacles **below ~30 cm** (manual height; TF says 20 cm — measure it) produce *no observation in any consumed data source*: not in /scan (physics), not in sonar (rear-only, unconsumed anyway), not in any secondary laser (URG dead), not in the static map (unless permanent and drawn). The first contact event is the bumper — whose firmware stall response is unverified and whose software handling is deliberately disabled. Historical incident forensics (obstacle height/speed/bumper event correlation) is not possible from retained logs: /diagnostics is not persisted and journal/syslog retention on both machines doesn't reach back to known incidents.

### 4.4 Classification (per brief's taxonomy)

**Primary: sensor blind spot** (physical, below the single 30 cm scan plane) **+ unused installed/optional sensor** (URG-04LX configured off, port nonexistent on current SBC). **Secondary: bumper safety handling unverified** (possible mis-wiring; software chain ignores bumper bits). *Not* supported by evidence: footprint error, TF/driver error for the main laser, costmap integration error, stopping-distance/velocity issue. Mapping limitation applies only to permanent low furniture (none confirmable remotely).

### 4.5 Safe remediation options

1. **Physically inspect for the URG-04LX** beneath the front bumpers (deferred test). If present: it cannot talk to the current SBC without a serial port it doesn't have — practical integration paths are a USB-serial adapter into the SBC (new ARIA laser config, protocol extension) or wiring it to the Pi 5 directly (urg_node2 → new `/scan_low` → costmap observation source + collision-monitor source). The Pi path avoids the 32-bit Xenial machine entirely and is the cleaner long-term option.
2. If absent: add a low-mounted forward sensor on the Pi (2D lidar or depth camera) as hardware remediation; until then, **reduce speed in blind-spot-sensitive areas** (Nav2 speed-limit zones via the already-loaded route/AdjustSpeedLimit or keepout/speed filters) and add **keepout zones for known permanent low obstacles**.
3. Verify and, if needed, repair bumper wiring; confirm `BumpStall` FLASH via µARCScf during the deferred physical session; then surface bumper hits into the safety chain (e.g., bridge maps a debounced bumper bit to a zero-velocity hold + ERROR diagnostic) — as a **last-resort layer, not the primary low-obstacle sensor**.
4. Correct the laser TF height (0.2 → measured ~0.3 m) for record accuracy.

## 6. Other findings

1. **SBC clock 5.29 years slow** while chrony is healthy and synced upstream — it needs a step (`makestep` / one-time manual step) and probably an RTC battery. Consequences today: unusable log timestamps, broken logrotate, journal correlation impossible. Robot data is unaffected (Pi stamps everything).
2. **Custom recovery BTs exist but are not referenced** by any param/launch — stock BT is silently in use. (Repo `navigate_recovery_always_try.xml` header says the opposite of what's deployed.)
3. **docking_server bypasses the whole safety chain** (publishes `/cmd_vel` directly) — dormant today, a trap tomorrow.
4. **patrolbot-server log drop-in silently ignored** (systemd 229 can't parse `append:`); volatile journal → no persistent SBC service logs.
5. Overnight **unclean SBC power loss** (~23:11 Jul 15 → ~15:51 Jul 16) of undetermined cause; syslog NUL corruption confirms power cut rather than shutdown. Worth asking the operator whether it was switched off intentionally.
6. Bridge/system resilience items verified healthy: queue back-pressure design, TF-before-scan ordering, `base_shift_correction: False` landmine documented and in place, `initial_transform_timeout` parking behavior, twist_mux priorities (safety 10 > joy/teleop 8 > switch 6 > nav 5).
7. Minor: teleop path (joy → mux → smoother → /cmd_vel) bypasses the collision monitor by design — operator assist only; worth remembering during dock tests. SBC serial leg fixed at 9600 baud (stock; latency floor). `ros` user on SBC is in `sudo`/`docker` groups (attack-surface note; out of scope).

### 7.1 Controlled dock-departure test

Required conditions: skilled operator; clear safety perimeter; second person at the hardware E-stop; robot initially docked; area behind the robot physically inspected and clear; rear sonar confirmed operational before motion; bumpers confirmed active; low initial speed; ROS and SBC logs being collected; ability to immediately disable motors; no unrelated cmd_vel publishers.

Recommended procedure:
1. Capture the docked scan, sonar, TF, costmap, pose, charging state, and motor state.
2. **First distinguish the inhibit source:** with the red E-stop buttons confirmed released, observe `/diagnostics` — if `estop_pressed` stays True while charging, the dock/charge mechanism asserts it; then verify that a µARCS `CHARGE 0` release (added via a controlled server change, or µARCScf session) de-asserts it. This resolves the remaining Concern-A ambiguity.
3. Confirm reverse velocity is permitted by every command-path component (per §3.2 today it is not — collision-monitor and controller changes must land first).
4. Confirm the rear path is clear in both sensor data and physical inspection.
5. Command only a very short, low-speed reverse departure; stop immediately after clearing the dock.
6. Verify the front-wall observation no longer prevents motion once clear; verify rear sonar stayed active throughout; verify no old velocity resumes after stopping (SBC watchdog log).
7. Repeat only after reviewing logs.

Success criteria: robot backs away without rotating into the wall; rear sonar and bumpers remain active; no collision-monitor violation; no stale obstacle blocks departure after physical clearance; motion stops immediately when commanded; docking and localization state remain valid.

Recommended procedure:

## 8. Conclusions (required questions)

1. **Can the PatrolBot safely leave the dock using reverse motion?** Not today. Motion while charging is inhibited at the hardware/firmware level (observed e-stop + motors-disabled), no component sends the µARCS CHARGE-release, the nav stack cannot command reverse (RPP `allow_reversing: false`; BackUp recovery unreachable in the deployed stock BT), and the front-scan-only stop box zeroes any nav command when the dock wall sits 0.25–0.30 m ahead. Teleop reverse would work *only after* charge release / e-stop clearance / motor enable.
2. **Is rear sonar used for dock departure and reverse protection?** No. It is published (5 Hz, real detections, correct geometry) but consumed by nothing in the motion-safety chain — display only.
3. **What component currently prevents dock departure?** Layered: charging/e-stop motor inhibit (primary) → missing undock sequence → no reverse capability in the controller/BT → direction-agnostic collision-monitor stop → invalid post-restart localization.
4. **Does the configured footprint match the real robot?** The body, yes — exactly (octagon from ARIA dims + swing radius, consistent across both costmaps, meters, correctly oriented and centered). Bumper envelope and modern attachments (Pi enclosure, antennas) are unmeasured — deferred.
5. **Can the main LiDAR physically detect the reported low obstacles?** No — anything below its single scan plane (~30 cm per manual) is physically invisible to it, at any parameter setting.
6. **Is an optional low-obstacle sensor installed?** Unconfirmed physically. Strong configuration evidence a URG-04LX was factory-fitted (populated per-robot params, "(installed in robot)" annotation), but it is configured not to connect and its serial port doesn't exist on the current SBC.
7. **If installed, is it fully utilized?** No — 0 %. Not connected, not read, not in the SBC→Pi protocol, absent from every costmap and safety source.
8. **Are low-object collisions caused by sensing coverage, parameters, stopping distance, bumper handling, or a combination?** Sensing coverage (physical blind spot + unused URG) is the primary cause; bumper handling is an unverified secondary layer. Parameters and stopping distance are adequate for what the sensors actually see; footprint/inflation are not causal.
9. **Which corrections can be made in software?** Undock sequence (server CHARGE-release + protocol + controlled reverse behavior); rear-sonar integration into collision monitor/costmap; wiring in the custom BT; direction-aware stop polygons; routing docking_server through the mux; AMCL dock-pose initialization; sonar-freshness monitoring; chrony `makestep`; fixing the server log drop-in; TF laser-height correction; speed-limit/keepout zones for known low-obstacle areas.
10. **Which limitations require hardware or sensor-coverage changes?** Forward low-obstacle sensing below the scan plane (connect/replace the URG — the current SBC lacks a port for it; attaching a low sensor to the Pi 5 is the practical route); bumper wiring repair if the constant bit proves a fault; SBC RTC battery.
11. **What must be validated physically before autonomous operation resumes?** The two deferred tests in §7: dock-inhibit mechanism identification and controlled reverse departure (§7.1), and the low-obstacle sensing/bumper survey including URG presence and true scan-plane height (§7.2).
